# DAYCUBE efficiency review, 2026-10-24

This pass reduces repeated database work, fixes growing caches and makes failed live writes
explicit. It continues `capture-browser-gaze`, after fetching and fast-forwarding from `eb473b0`
to `addded7497c46ece826bb8e84210d4e1fd27d6d7`. The incoming notes, graph and capture work was
preserved. No personal vault, recordings or webcam frames were used in the benchmarks.

DeepInfer supplies engineering patterns, not a comparable speed target for this application.
There is no workload/hardware comparison establishing performance parity. No codebase can be
certified as having its maximum possible speed by a source review or these synthetic tests.

by line. A complete visual, dependency, native-library or every-source-line audit is not claimed.

Treatment of other files:

- Generated models/bindings: reproduce from the eight canonical schemas and run consistency and
  cross-language validation checks; do not hand-optimize generated output.
- Assets and fonts: inventory hashes/bytes and preserve the visual design. No media inspection or
  dependency-code audit is implied.
- Lockfiles: parse/inventory and retain reproducible dependency resolution; no arbitrary version churn.
- Fictional fixtures: preserve their identities and compare derived results. The executable stage
  builders in `sampleDay.ts` were reviewed separately from its embedded example records.
- Historical measurements: retain their original provenance and limitations. New results have new
  filenames; a previous gaze/capture measurement does not describe the currently running services.
- Documentation: retain as context/provenance, not executable performance evidence. No vendored source
  is tracked; dependency internals in installed environments are outside this review.

## Correctness and failure handling

- Vector generation lookup, block loading and rescoring use one SQLite WAL read snapshot. A test
  commits a replacement between candidate selection and rescore and checks stable results.
- Retrieval tolerates deleted keyword/vector candidates. Rewritten/deleted notes cannot return
  old chunk text; file freshness compares size as well as modification time.
- Extension delivery is single-flight. Records reach durable storage before POST; a stalled
  response or malformed success body keeps them queued. Header and JSON-body consumption share
  a five-second AbortController deadline; all callers clear their owned timer.
- Ask and Rebuild use the day currently open. Speaker confirmation uses the active moment ID.
  Failed live renames/confirmations remain errors and update display state only after success.
  Error dialogs suspend rendering. Unsupported time-range deletion neither hides records nor
  invents a deletion audit; the development shim also returns 501 and retains no fake history.
- Out-of-calendar search ranges return a client error rather than an unhandled overflow.
- Model generation uses the committed Ruff configuration and writes LF output. Windows fixture
  reads specify UTF-8 where needed; freshness tests advance a fake clock through the documented
  two-second interval. An older browser assertion now includes the newer capture-only fixture day.

## Viewer observations

The [production viewer report](../eval/results/viewer-review-2026-10-24.json) serves built assets
from an owned loopback server. Every API route returns an explicit synthetic 503, so the viewer
uses its bundled sample and never contacts the personal vault. It records bundle hashes, three
fresh-context calendar/stage loads, warm reloads and 30 seconds of playback in each renderer.

The calendar requests zero bytes from the Three.js chunk; opening the stage requests its
833,096-byte file (833,396 transferred with HTTP overhead); warm reload requests zero transferred
bytes for it. This verifies the incoming lazy-loading work, not a new startup speedup. The chunk
still costs parse/initialization time. The build continues to warn about its size.

The renderer is **SwiftShader**, not the workstation's actual GPU. Both renderers produce zero
draws in the settled 600 ms idle window. Playback task time, draw counts, short-term heap changes
and ready times are observations on this software renderer, not a real-GPU frame-rate guarantee.
The final-source sample retained roughly 2.83 MB more JS heap in 3D after 30 seconds and
collection, and 0.21 MB more in 2D. Measured main-thread task time was 19.72 s (3D) and 1.32 s
(2D), including 0.545 s and 0.747 s of script time respectively. Calendar-ready median was
96.8 ms, first-stage-ready 334.1 ms and warm-stage-ready 307.1 ms on unthrottled localhost;
these include Playwright polling. Missing early paint entries stay null. These are follow-up
signals, not proof of a leak or a bound.

## Remaining limits and blocked measurements

1. **Real GPU and long sessions:** SwiftShader cannot establish the user's GPU frame latency,
   interactive memory ceiling or GPU allocation behavior. Hours-long 2D/3D traces, modal animation
   cleanup and large-day geometry remain open. The sample's short heap growth deserves a steady-state
   trace before another optimization. No design changes were made to chase synthetic timings.
2. **Large histories:** full note-folder/day/capture freshness scans and data-center byte walks
   remain proportional to history size. Per-path write versions and current-folder note inventories
   retain state proportional to distinct files. Cache budgets do not eliminate those costs.
3. **Live-data boundaries:** the moment and gaze inspector still contain prototype fallbacks;
   some display interfaces require a fake location where live data may be unavailable. A dedicated
   migration must preserve explicit unavailable/source metadata. New derived API response definitions
   also still need canonical JSON Schemas rather than parallel handwritten definitions.
4. **Continuous resources:** capture/browser queues have count caps, not complete byte budgets;
   reading visit paths can grow until a visit ends. The gaze sender is process-owned without an
   explicit close method, and native camera calls may outlive join timeouts. Browser password/shadow
   scans run repeatedly; caching them without privacy-correct invalidation would be unsafe.
5. **Concurrency:** same-day API admission is per process. Multi-process writers, keyword-query
   snapshots, capture-only manual reindex admission and aggregate memory under concurrent different-day
   work need larger integration tests. Multi-file capture append failures are not a single transaction.
6. **Device acceptance:** no camera was opened, no calibration or autostart was changed, and live
   capture was not paused/restarted. Full extension/receiver tests bind port 7700, occupied by the
   live service, so they were source-reviewed but not run. Opera reload, lock/unlock, video-call camera
   handoff, real paragraph placement and sign-out/sign-in remain manual acceptance work.
7. **Optional jobs/datasets:** paid cloud/model calls were not authorized for benchmarking. There
   is no comparable DeepInfer multi-GPU deployment or supplied external face-gaze dataset here.
   Model residency, GPU memory, frame batching and end-to-end remote latency remain unmeasured.
   Offline evaluation tools also have remaining scratch/figure/npz cleanup and input-validation gaps,
   identified per file in the ledger.
